ParkFlow — implementation security and readiness review
2026-10-07

Scope and conclusion
Compared the implementation with docs/superpowers/plans/2026-10-07-platform-management.md and the approved launch-readiness.txt proposal. This is a source review plus the targeted execution evidence below, not a production security certification. Significant pilot protections are implemented; public production acceptance still has explicit gates. No secret values were inspected, no live payments or external messages were sent, and SMS follow-up remains suspended.

Implemented protections inspected
1. Vehicle access: self-added/relinked plates become unverified drivers. Violation details, evidence and permits require verified access; association alone does not grant ownership. Admin review requires a 10–500-character reason, records an audit, and revocation clears verification and returns the role to driver. The bilingual UI confirms person, plate, role and evidence reference before submission.
   Evidence: server/src/modules/vehicles/service.ts:6,19; modules/violations/service.ts:12; modules/vehicleVerification/service.ts:22; app/admin/vehicles.tsx.
   Final review found and fixed two remaining paths: violation notifications now target verified active associations only, and the legacy admin vehicle-grant endpoint now requires and audits the review reason. Evidence: server/src/modules/admin/service.ts:42,78; modules/admin/routes.ts:40. Existing historical notifications are not retrospectively erased.

2. Inventory: a transactional zone-wide pool respects explicit physical vacancy/occupancy, full/unknown state, fresh authenticated OPERATOR or ADMIN counts, overlapping commitments, and a 500-token cap. Checked-in demand is reconciled against snapshot/check-in timestamps conservatively. SENSOR/ANPR sources are not accepted by the manual provider; ADMIN counts do not claim an operator-backed guarantee. Tokens describe allocations, not surveyed empty bays.
   Evidence: server/src/modules/inventory/manualProvider.ts:15,37,97; modules/reservations/service.ts. Summing overlapping commitments can under-offer capacity for a long window; no departure forecast or physical sensor integration was proven.

3. Session/location integrity: active published lifecycle is required for public search/details/code lookup and new sessions/reservations. Prepaid starts and extensions reject closure overlap; ending exactly at closure start is allowed. Extensions retain original pricing snapshots. Start-stop initiation checks the current instant; no automatic termination at a later closure was added. Lock order is zone→vehicle/session/hold→wallet where applicable; no reverse acquisition was found in the reviewed flows.
   Evidence: server/src/modules/sessions/service.ts:14,19,56; modules/parking/service.ts; modules/parking/layouts.ts. Reservation cancellation now conditionally updates confirmed future bookings under transaction/locks, preserving a concurrent check-in (modules/reservations/service.ts:174).

4. Administration: shared operator/zone action permissions separate owner, manager and attendant; existing admin aliases delegate management mutations through that boundary. Version checks reject stale edits; disruptive changes inspect existing use; owners submit locations for admin publication. New locations use live/manual, non-prototype inventory. Last-admin and permission-change session revocation guards are present.
   Evidence: server/src/modules/management/permissions.ts; modules/management/service.ts; modules/admin/service.ts:63. This paragraph records source inspection, not a fresh execution of every management scenario.

5. Admin sessions now have an absolute eight-hour family lifetime in both authenticate and refresh. Rotated/revoked ancestors establish the original deadline, and expiry revocation commits before the denial is thrown. Ordinary-user lifetime is unchanged. Legacy public road/parking report responses remove stable reporter IDs.
   Evidence: server/src/modules/auth/service.ts:13,77,98; modules/roads/service.ts:7,18.

6. CMS boundaries: ADMIN-only draft/history/publish/rollback routes; strict bounded schema; plain localized text, fixed action paths, HTTPS image URLs without embedded credentials, hex colors. Public responses expose validated published configuration only. Global lock/version checks guard publication; publishing and rollback append revisions and audit events. The renderer uses Text/Image components, not executable HTML. Revision immutability is enforced by service behavior; this does not establish protection against direct database-administrator tampering. External images are client-fetched, not server-fetched.
   Evidence: server/src/modules/appConfig/{schema,service,routes}.ts; src/types/appConfig.ts; src/components/brand/ConfiguredWelcome.tsx; src/store/appConfigStore.ts.

7. Payment recovery persists a user-scoped logical top-up key/payload before sending and retains ambiguous outcomes; changed payloads cannot silently replace a pending operation. Existing server ledger, idempotency, webhook-signature and amount/currency checks remain. Production configuration rejects development payments, but a real card SDK/tokenization and gateway acceptance are still outstanding.
   Evidence: src/utils/pendingPayment.ts; src/services/http/walletService.ts; server/src/modules/wallet/service.ts; server/src/providers/payments.ts; server/src/config/env.ts. Cross-tab/device recovery and real provider behavior were not exercised in this review.

- HttpOnly/Secure/SameSite web session design with CSRF protection as appropriate. Current web storage falls back to JavaScript-readable AsyncStorage (src/services/storage.ts:28); native storage uses SecureStore. No XSS exploit was demonstrated.
- Real provider card capture/tokenization, gateway settlement/refund and ambiguous-result acceptance; owner payouts/subscriptions are not delivered by operational analytics or internal wallet adjustments.
- Production HTTPS/origins/CSP validation, managed database/Redis/object-storage permissions, secret provisioning, monitoring, backup/restore drills, recovery targets and incident procedures. Local tests do not validate these external infrastructure controls.
